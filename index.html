Abstract

Code policies, which are Python programs that control an agent's actions, may fail when their assumptions do not match the environment. Repairing such failures requires execution feedback, while repeated model invocations increase inference cost. We introduce Adaptive Policies, which extend generated Python policies with checkpoints that trigger model-assisted repair when execution fails. Repair escalates from local recovery to helper regeneration and task re-planning. We evaluate Adaptive Policies against ProgPrompt and Code as Policies (CaP) in the VirtualHome household simulator using two open-weight language models, Qwen3.5-9B and Gemma 4 12B. Adaptive Policies achieves task success rates of 24.3% and 24.6%, compared with 13.0% and 8.9% for our CaP baseline. However, it does not consistently outperform ProgPrompt and requires more model invocations. Enabling extended reasoning does not consistently improve success under the evaluated output budget and substantially increases generation time. These results show that execution-time repair improves the success of generated code policies, but its benefits depend on producing executable code and come at an additional inference cost.

An Episode

Approach

Code-generating planners already turn instructions into programs. ProgPrompt writes a straight-line program whose assertions trigger recovery steps written in advance; the model is not asked to revise the plan during execution. Code as Policies can express reactive behaviour through conditions, loops and helper functions. In our adaptation, many generated policies return early after a failed guard, while some index empty object-query results before acting. These are behaviours of the generated programs, rather than restrictions on what Code as Policies can express.

Adaptive Policies extend the code-policy approach in Code as Policies with execution checks and model-assisted repair. Generated policies state expected conditions as checkpoints: 

def policy():
    find("fridge")
    fridge = checkpoint("a fridge is visible",
                        lambda: [o for o in get_visible_objects() if o.name == "fridge"])[0]
    open(fridge)
    checkpoint("the fridge is open", lambda: "OPEN" in (get_object_states(fridge) or ()))

checkpoint(description, check) runs an ordinary Python check over the observation API and returns its value, so assignments receive fresh object references. A failed checkpoint, a failed action or an exception in generated code starts recovery. The model sees the failure, the agent's current observation, the running code, its local variables and the recent execution history, and the repair escalates only as far as needed:

  1. Local recovery. A short recover() program fixes the immediate problem, and the checkpoint is evaluated again.
  2. Helper regeneration. The failing helper function is rewritten and replaces the old definition for the rest of the episode.
  3. Re-planning. A continuation policy() completes the rest of the task from the current state, in the same episode.

Repeated failures without a successful action end the episode as making no progress, and every task runs under a time and model-call budget. To examine checkpoints and failure handling, we compare three placements of the points where the model can be called again. Evaluation

All methods act in VirtualHome, where the agent only observes the objects in its current room, on the 45 evaluation task entries of the ProgPrompt suites: seen and unseen tasks, tasks with ambiguous goals, and two new household scenes. We use Qwen3.5-9B and Gemma 4 12B, hybrid open-weight models whose reasoning can be switched on or off with the same weights, at three sampling temperatures. Every intended task counts towards success rate, partial success rate and executability, and we record model calls, time and tokens, and operational outcomes. The player is a modified VirtualHome v2.3.0 build with symbolic observations. Inconsistent reference task graphs were repaired; Claude Code and Codex assisted with experiment design and those repairs.

  • Episodes make progress after repair. Adaptive Policies' first-failure snapshots score 13.5% (Qwen) and 6.0% (Gemma), compared with final success rates of 24.3% and 24.6%. These snapshots describe subsequent progress; they do not isolate a causal recovery effect.
  • Performance relative to ProgPrompt is mixed. Adaptive Policies' pooled success is 2.7 percentage points lower for Qwen and 2.7 higher for Gemma. ProgPrompt retains the highest partial success and executability for both models. No equivalence or significance claim is made. Implicit checkpoints have Qwen's highest observed AP success; explicit checkpoints have Gemma's.
  • Repair requires additional inference. Adaptive Policies averages 10.9 Qwen and 8.1 Gemma model calls per trial, with medians of 5 and 4. ProgPrompt averages 4.4 and 3.9; CaP averages 3.3 for both. Failure-free execution needs no repair call, but policy generation and queries still have costs.
  • Invalid code limits execution-time repair. Invalid or truncated initial code prevents runtime repair in about a quarter of AP trials; invalid or truncated continuations also cause failures. No method achieves the annotated goals on the ambiguous suite, which does not imply that every generated interpretation is unreasonable. Extended reasoning substantially increases generation time without a consistent success gain under the evaluated output budget.

Comparisons evaluate complete methods: prompts, feedback, continuation after known action rejections and runtime budgets differ. There is one attempt per task-condition, and task identities recur across settings. Scene comparisons also differ in task composition and annotation. These experiments do not isolate transfer or establish a cost advantage over per-step re-planning, which was not evaluated. The report gives the full protocol and limitations.
