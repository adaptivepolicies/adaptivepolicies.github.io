Abstract

Large language models (LLMs) can translate natural-language instructions into action sequences for embodied agents, but the plans they produce are often incomplete, unexecutable or ungrounded in what the agent can observe. Planners that repair plans with feedback are more reliable, but they call the model again at every step, which makes them slow and costly. We propose adaptive policies: the model writes a Python policy once, in the style of Code as Policies, and the policy states its expectations as checkpoints that are checked against the agent's observations while it runs. A checkpoint that passes costs no model call. When a checkpoint, an action or the generated code fails, the model is invoked with the failure, the current observation and the running code, and the repair escalates from a local recovery step, to regenerating the failing helper function, to re-planning the rest of the task. We evaluate adaptive policies in the VirtualHome household simulator on the ProgPrompt task suites against two code-generation baselines, ProgPrompt and Code as Policies, using open-weight hybrid models with their built-in reasoning switched on and off.

An Episode

Approach

Code-generating planners already turn instructions into programs. ProgPrompt writes a straight-line program whose assertions trigger recovery steps written in advance, so a wrong assumption about where an object is cannot be corrected once the plan is written. Code as Policies writes a reactive policy that observes and checks action results, but when it meets a situation it did not anticipate it can only stop. In our baseline experiments, most failed Code as Policies trials were policies that had correctly detected that they could not continue.

Adaptive policies keep the policy written once, and turn those points of failure into checkpoints where the model is called again: 

def policy():
    find("fridge")
    fridge = checkpoint("a fridge is visible",
                        lambda: [o for o in get_visible_objects() if o.name == "fridge"])[0]
    open(fridge)
    checkpoint("the fridge is open", lambda: "OPEN" in (get_object_states(fridge) or ()))

checkpoint(description, check) runs an ordinary Python check over the observation API and returns its value, so assignments receive fresh object references. A failed checkpoint, a failed action or an exception in generated code starts recovery. The model sees the failure, the agent's current observation, the running code, its local variables and the recent execution history, and the repair escalates only as far as needed:

  1. Local recovery. A short recover() program fixes the immediate problem, and the checkpoint is evaluated again.
  2. Helper regeneration. The failing helper function is rewritten and replaces the old definition for the rest of the episode.
  3. Re-planning. A continuation policy() completes the rest of the task from the current state, in the same episode.

Repeated failures without a successful action end the episode as making no progress, and every task runs under a time and model-call budget. Evaluation

All methods act in VirtualHome, where the agent only observes the objects in its current room, on the 45 evaluation tasks of the ProgPrompt suites: seen and unseen tasks, tasks with ambiguous goals, and two new household scenes. We use Qwen3.5-9B and Gemma 4 12B, hybrid open-weight models whose reasoning can be switched on or off with the same weights, at three sampling temperatures. Every intended task counts towards success rate, partial success rate and executability, and we record model calls, time and tokens, and the cause of every failure.
